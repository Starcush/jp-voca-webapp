# 단어장 앱 제품/디자인 기획안

이 문서는 디자인 외주 또는 제품 방향 논의를 위해 현재 진행 상태, 앞으로의 기획, 페이지별 화면 요구사항을 정리합니다.

## 프로젝트 성격 정의

이 프로젝트는 크게 키울 사업이 아니라, 재미있어서 꾸준히 만들어가는 사이드 프로젝트입니다. 의사결정의 기준은 대규모 성장보다 실제 사용성과 지속 가능성입니다.

목표는 다음 세 가지입니다.

- 서버비와 OCR/AI API 비용 정도를 자체적으로 충당한다.
- 스터디 모임, 가족, 가까운 학습자처럼 실제로 써주는 사용자를 확보한다.
- 개발 포트폴리오이자 개인 일본어 학습 도구로서 충분한 가치를 만든다.

따라서 대박 사업을 전제로 한 의사결정은 하지 않습니다. 대규모 B2B 라이선싱, 전면 다국어 확장, 완전 구독형 모델, 복잡한 어드민/결제 시스템은 지금의 기준이 아닙니다. 작은 사용자 집단이 실제로 계속 쓰는 앱을 먼저 만듭니다.

## 1. 제품 개요

### 프로젝트명

- 현재 레포명: `jp-voca-webapp`
- 제품명 후보:
  - Tangocho
  - 단어장
  - 독해 노트
  - 사진 단어장
  - 일본어 문장 노트

### 한 줄 설명

사진과 문장에서 일본어 단어, 표현, 문법을 뽑아내고, 노트/시트/복습/독해 콘텐츠로 이어주는 일본어 학습 앱입니다.

### 만들고 있는 이유

일본어 학습자는 책, 문제집, 신문, 소설, 간판 등을 보다가 모르는 단어와 표현을 자주 만납니다. 기존 단어장은 단어를 직접 입력해야 하거나, 문장 안에서 쓰이는 문법/뉘앙스를 저장하기 어렵습니다.

이 앱은 사용자가 공부 중 만난 일본어를 사진이나 문장으로 가져오고, 필요한 단어/표현/문법을 쉽게 저장하고, 나중에 노트별로 훑고 복습할 수 있게 하는 것을 목표로 합니다.

### 핵심 사용자

- 일본어를 공부하는 한국어 사용자
- 책/문제집/일본어 원문을 직접 읽는 학습자
- 단어뿐 아니라 문법, 표현, 뉘앙스까지 정리하고 싶은 사용자
- 아이패드나 데스크탑에서 단어를 많이 훑어보고 싶은 사용자

### 제품의 핵심 흐름

```text
사진 찍기 또는 문장 입력
-> 텍스트 추출
-> 문장 보기
-> 단어/표현 선택
-> 읽기와 뜻 채우기
-> 저장 전 확인
-> 노트에 저장
-> 목록/시트/복습으로 학습
```

## 3. 현재 작업 중인 UX 방향

현재 가장 큰 문제는 기능이 늘어나며 버튼이 많아지고, 단어/문장보다 조작 UI가 더 크게 보이는 점입니다.

### 개선 방향

- 단어와 문장을 화면의 주인공으로 둔다.
- 버튼은 상시 노출하지 않고 필요할 때 펼친다.
- 노트 수정/삭제는 항상 보이지 않고 관리 메뉴 안에 둔다.
- 단어 목록 상단은 검색, 노트, 최소한의 컨트롤만 유지한다.
- 복습/시트/정리는 별도 역할을 가진 화면으로 분리한다.

### 최근 반영 중인 변경

- 선택된 노트의 이름 수정/삭제 버튼을 기본 숨김 처리
- `관리` 버튼을 눌렀을 때만 노트 관리 패널 표시
- 단어 목록 상단의 보기/필터/더보기 옵션을 접는 구조로 변경

## 4. 앞으로의 큰 기획 방향

### 4.1 OCR 플로우 고도화

현재 OCR은 텍스트 추출과 표현 저장까지 가능합니다. 다음 단계는 저장 전 확인과 문장 분석 UX를 더 다듬는 것입니다.

필요한 것:

- OCR 버튼 라벨 정리
- 문장 분리 결과 수정
- 문장 합치기/나누기
- 저장 전 확인 목록의 밀도 개선
- 읽기 없음/뜻 없음/필수값 누락 상태 표시
- 표현이 많을 때도 편하게 검토할 수 있는 UI

### 4.2 문법/표현 카드

일본어 학습에서는 단어보다 문장 안의 문법 패턴과 뉘앙스가 중요할 때가 많습니다.

예:

```text
暗め
= 暗い + 〜め
= 조금 어두운 편 / 어두운 쪽에 가까운
```

저장 후보 타입:

- 단어
- 문법
- 표현
- 문장

문법 카드에 필요한 정보:

- 문법 패턴
- 의미
- 접속 방식
- 원문 예문
- 해석
- 원어민 선호 표현 코멘트
- 비슷한 예문
- 헷갈리는 표현
- 난이도
- 태그

원어민 선호 표현 코멘트는 한국어 학습자가 사전적으로 아는 유사어 대신, 실제 일본어 원어민이 그 상황에서 자연스럽게 고를 표현을 짚어주는 짧은 설명입니다. AI가 후보를 제안하고 사람이 검수하는 방식으로 운영합니다.

### 4.3 시트 보기

카드형 단어장은 한 단어씩 보기 좋지만, 아이패드/데스크탑에서 많이 훑기에는 불편합니다. 별도의 시트형 학습 보기가 필요합니다.

역할:

- 단어를 한 화면에 많이 보여준다.
- 노트별로 훑는다.
- 뜻/읽기/예문 표시를 토글한다.
- 나중에 CSV/Excel export로 확장한다.

예상 컬럼:

- 일본어: 단어, 읽기, 뜻, 예문
- 중국어: 단어, pinyin, 뜻, 예문
- 영어: 단어, 뜻, 예문

### 4.4 근대문학 독해 콘텐츠

퍼블릭 도메인 일본 근대문학을 앱 안에서 읽고, 문장별 번역/해설/문법/문체 설명을 제공하는 콘텐츠입니다.

핵심은 사용자가 매번 AI를 실행하는 것이 아니라, 운영자가 AI로 초벌 분석 후 저장해둔 공용 콘텐츠를 보여주는 것입니다.

가능한 화면:

- 작품 목록
- 작품 소개
- 독해 뷰어
- 문장 해설 패널
- 단어/문법/표현 도움
- 작가 문체 설명

주의:

- 원문이 퍼블릭 도메인인지 확인
- 번역/해설/주석은 직접 제작하거나 별도 권리를 확인
- 출처 표기 필요

### 4.5 소셜 로그인, 크레딧, 어드민

서비스화 시 필요한 장기 기획입니다. 다만 현재는 소셜 로그인과 정식 어드민을 바로 만들지 않고, 먼저 크레딧 시스템 최소 버전과 사용량 제한을 검증합니다.

계정:

- Google 로그인
- Apple 로그인
- 이메일 계정과 소셜 계정 연결

크레딧:

- OCR 요청
- AI 읽기/뜻 요청
- 표현 분석 요청
- AI 독해/퀴즈 요청
- 무료 월 기본 크레딧
- 충전 또는 구독

어드민:

- 유저 목록
- 유저 상세
- 로그인 방식
- 크레딧 잔액
- 사용량 기록
- 크레딧 수동 지급/차감
- 유저 상태 관리
- 환불/결제 내역, 결제 도입 이후

### 4.6 상황극 프롬프트 생성

저장된 단어 또는 노트를 선택하면, 사용자가 ChatGPT 같은 외부 LLM에 붙여넣을 수 있는 상황극 프롬프트를 생성합니다.

원칙:

- 앱이 직접 AI API를 호출하지 않는다.
- 텍스트 프롬프트만 조립해 클립보드로 제공한다.
- API 비용이 들지 않으므로 무료 또는 최소 크레딧 기능으로 둔다.
- 프롬프트 템플릿은 클라이언트에 직접 노출하지 않고 서버 사이드에서 조립한다.
- 단어 수가 많을 경우 앱이 직접 클러스터링하지 않는다.
- 50개 이상처럼 항목이 많으면 ChatGPT 자신에게 의미 단위로 그룹을 나누고 순차 진행하도록 지시한다.

목표:

- 사용자가 저장한 단어를 실제 회화/상황극으로 써보게 한다.
- 앱 안에서 비싼 AI 대화를 제공하기 전, 비용 없는 방식으로 학습 가치를 검증한다.

### 4.7 비즈니스 모델

현재 목표는 대규모 수익화가 아니라, 서버비와 API 비용을 감당할 정도의 지속 가능성입니다.

기본 정책:

- 기본 저장, 복습, 노트, 시트 보기는 완전 무료로 유지한다.
- OCR, AI 읽기/뜻 자동완성, 문법 분석처럼 실제 인프라 비용이 드는 기능에만 크레딧을 사용한다.
- 상황극 프롬프트 생성은 앱이 직접 AI API를 호출하지 않으므로 무료 또는 최소 크레딧으로 둔다.
- 인앱 AI 대화처럼 앱 안에서 직접 챗봇이 응답하는 기능은 크레딧 결제 시스템이 안정적으로 검증된 이후에만 장기 옵션으로 검토한다.

크레딧 MVP:

- 월 무료 크레딧 N개를 지급한다.
- 크레딧 소진 시 OCR/AI 기능 이용을 제한한다.
- 복잡한 결제/충전은 1차 범위에서 만들지 않는다.
- 가족, 테스트 유저, 개발자 계정은 화이트리스트로 무제한 처리할 수 있게 한다.
- 화이트리스트는 DB 컬럼 하나 또는 이메일 목록 수준으로 시작한다.
- 별도 어드민 UI는 만들지 않는다.

## 5. 페이지별 기획안

### 5.1 로그인/가입 페이지

목적:

- 사용자가 빠르게 계정을 만들고 기존 계정으로 돌아올 수 있게 한다.

현재 기능:

- 이메일/비밀번호 가입
- 이메일/비밀번호 로그인
- 비밀번호 재설정

향후:

- Google 로그인
- Apple 로그인
- 이메일 계정과 소셜 계정 연결

디자인 포인트:

- 모바일에서 입력창이 너무 중앙 아래로 밀리지 않게 한다.
- 가입/로그인 전환이 명확해야 한다.
- 왜 이메일이 필요한지 간단히 안내한다.

### 5.2 언어 선택 온보딩

목적:

- 사용자가 학습할 언어를 선택하고 기본 언어를 설정한다.

현재 기능:

- 일본어/영어/중국어 선택
- 첫 번째 선택 언어를 기본값으로 사용

디자인 포인트:

- 국기/언어명을 시각적으로 명확하게 보여준다.
- 여러 언어 선택 가능성을 자연스럽게 보여준다.
- 나중에 설정에서 추가/변경 가능하다는 느낌을 준다.

### 5.3 단어 목록 페이지

목적:

- 저장된 단어를 보고, 검색하고, 노트별로 훑는 메인 화면입니다.

현재 기능:

- 언어 탭
- 노트 선택
- 검색
- 보기 모드
- 상태 필터
- 단어 카드 목록
- 사진에서 가져오기
- 단어 정리 진입

현재 UX 문제:

- 버튼이 많아 단어보다 조작 UI가 더 크게 보인다.
- 보기 모드가 꼭 핵심인지 재검토 필요.
- 노트 관리 버튼이 상시 노출되면 화면 밀도가 떨어진다.

개선 방향:

- 단어/뜻/예문을 더 잘 보이게 한다.
- 보기 모드와 필터는 접어서 보여준다.
- 노트 수정/삭제는 관리 메뉴 안에 둔다.
- 복습은 별도 페이지 역할로 분리한다.

디자인 포인트:

- 모바일에서는 검색과 노트가 가장 중요하다.
- 카드 높이를 과하게 키우지 않는다.
- 버튼보다 단어 콘텐츠가 먼저 보여야 한다.

### 5.4 단어 카드

목적:

- 단어, 읽기, 뜻, 예문, 학습 상태를 보여준다.

현재 기능:

- 단어/읽기 표시
- 뜻 표시
- 예문/예문 번역 표시
- 수정 진입
- 알았어요/모르겠어요 상태 변경
- 가리기 모드에서 공개

현재 UX 문제:

- 카드 안 버튼이 많아질 수 있다.
- 수정 버튼이 항상 보일 필요가 있는지 재검토 필요.

개선 방향:

- 단어/읽기/뜻이 먼저 보이게 한다.
- 수정/삭제/노트 이동은 `...` 메뉴로 숨기는 방향 검토.
- 알았어요/모르겠어요도 복습 페이지로 더 넘길 수 있는지 검토.

### 5.5 노트 영역

목적:

- 책/시험/수업/주제 단위로 단어를 묶는다.

현재 기능:

- 전체/미분류/노트 탭
- 새 노트 생성
- 이름 수정
- 삭제

개선 방향:

- 노트 선택 UI와 노트 관리 UI를 분리한다.
- 이름 수정/삭제는 항상 보이지 않게 한다.
- 노트별 단어 수, 최근 추가일, 복습 대상 수 표시를 검토한다.

### 5.6 단어 추가 페이지

목적:

- 사용자가 직접 단어를 저장한다.

현재 기능:

- 단어/읽기/뜻/예문/예문 번역 입력
- 읽기 자동 생성
- 저장될 노트 안내

디자인 포인트:

- 필수/선택 필드가 명확해야 한다.
- 저장될 노트가 분명히 보여야 한다.
- 모바일 입력이 편해야 한다.

### 5.7 OCR 사진 가져오기 페이지

목적:

- 사진에서 텍스트를 추출하고, 문장에서 표현을 골라 단어장에 저장한다.

현재 기능:

- 이미지 선택
- 텍스트 추출
- 추출 텍스트 수정
- 문장별 보기
- 표현 선택
- 저장 전 목록에 담기
- 읽기/뜻 채우기
- 진행률 표시
- 저장

현재 UX 문제:

- 버튼 라벨이 아직 덜 명확하다.
- 저장 전 목록이 길어질 때 검토가 어려울 수 있다.
- 문장 분리 결과를 직접 조정하는 기능이 부족하다.

개선 방향:

- `문장에서 표현 고르기`
- `저장 전 확인`
- `읽기·뜻 채우기`
- 문장 수정/합치기/나누기
- 저장 전 확인 목록 compact UI

### 5.8 단어 정리/노트 이동 페이지

목적:

- 단어를 대량으로 보고, 검색하고, 다른 노트로 옮긴다.

현재 기능:

- 출발 노트 선택
- 도착 노트 선택
- 단어 검색
- 다중 선택
- 노트 이동

디자인 포인트:

- 관리용 화면이므로 카드보다 밀도 높은 리스트가 적합하다.
- 한 화면에 많은 단어를 보여줘야 한다.
- 셀렉트/버튼이 모바일 너비를 넘지 않아야 한다.

### 5.9 복습 페이지

목적:

- 저장한 단어를 기억하는지 확인한다.

현재 기능:

- 노트별 복습
- 모르는 단어 중심 복습
- 알았어요/모르겠어요 처리

개선 방향:

- 복습 모드 다양화
- 오래 안 본 단어
- 계속 모르는 단어
- 노트별 집중 복습
- 복습 완료 후 요약

### 5.10 시트 보기 페이지

목적:

- 아이패드/데스크탑에서 단어를 한 번에 많이 훑으며 공부한다.

상태:

- 아직 구현 전

필요 기능:

- 노트별 시트 보기
- 단어/읽기/뜻/예문 컬럼
- 뜻 가리기
- 읽기 가리기
- 예문 표시/숨김
- 검색
- 나중에 CSV/Excel export

디자인 포인트:

- 카드형보다 훨씬 밀도 높게.
- 태블릿에서 보기 편하게.
- 행 높이를 안정적으로.
- 학습용이므로 너무 업무용 테이블처럼 차갑지 않게.

### 5.11 문장/문법 분석 페이지 또는 패널

목적:

- 문장 안의 단어, 문법, 표현, 뉘앙스를 분석한다.

상태:

- 아직 기획 단계

예시:

```text
写真は暗めだけど、雰囲気はいい。
```

분석 후보:

- 暗め: 暗い + 〜め
- 〜め: 조금 ~한 편
- だけど: ~이지만
- 雰囲気: 분위기
- 雰囲気がいい: 분위기가 좋다

디자인 포인트:

- AI 결과는 바로 저장하지 않고 사용자가 선택하게 한다.
- 단어/문법/표현 타입을 명확히 구분한다.
- 문법 카드는 접속 방식과 뉘앙스 설명이 중요하다.

### 5.12 근대문학 독해 뷰어

목적:

- 퍼블릭 도메인 근대문학을 앱 안에서 읽고, 문장별 해석/문법/문체 도움을 제공한다.

상태:

- 기획 단계

핵심 구조:

```text
작품
-> 챕터
-> 문단
-> 문장
-> 해석/현대어/문체/문법 도움
```

기본 UX:

- 기본 화면은 원문 중심
- 글자 크기 조절
- 줄 간격 조절
- 원문/번역 토글
- 문장 클릭 시 해설 패널 표시
- 모바일은 bottom sheet
- 아이패드/데스크탑은 side panel

콘텐츠 제작 방식:

- 퍼블릭 도메인 원문 확보
- 문장 단위 분리
- AI로 초벌 번역/해설 생성
- 사람이 검수 또는 수정
- 앱 DB에 저장
- 사용자는 저장된 해설을 빠르게 열람

주의:

- 원문 저작권 확인
- 번역/해설/주석은 직접 제작하거나 권리 확인
- 출처 표기

## 6. 디자인 원칙

- 텍스트가 주인공이다.
- 버튼은 항상 보이지 않아도 된다.
- 주요 액션과 보조 액션을 분리한다.
- 모바일에서는 한 화면의 버튼 수를 줄인다.
- 카드형, 시트형, 복습형, 독해형 화면의 역할을 분명히 한다.
- 학습자는 “입력”보다 “읽고 이해하고 저장하는 흐름”에 집중해야 한다.

## 7. 우선순위 제안

우선순위는 “이 앱을 왜 써야 하는지 한 문장으로 설명 가능한 상태”를 먼저 만드는 방향으로 재편합니다. 현재 기준의 한 문장은 다음과 같습니다.

```text
사진과 문장에서 일본어 단어, 문법, 표현을 뽑아 노트로 저장하고, 비용 걱정 없이 복습과 상황극 학습까지 이어주는 개인 학습 앱
```

### 1차 범위: 유저 확보용 MVP, 지금 당장 착수

1차 범위는 실제 사용자에게 열어볼 수 있는 최소 상태를 만드는 단계입니다.

#### 1. 크레딧 시스템 최소 버전

왜 이 순서인가: OCR/AI 기능을 여러 사용자에게 열기 전 API 비용 리스크를 막아야 하기 때문입니다.

범위:

- OCR/AI 기능에만 크레딧을 적용한다.
- 기본 저장, 복습, 노트, 시트 보기는 무료로 둔다.
- 복잡한 결제/충전 없이 월 무료 크레딧 N개를 지급한다.
- 크레딧 소진 시 OCR/AI 기능 이용을 제한한다.
- 가족, 테스트 유저, 개발자 계정은 화이트리스트로 무제한 처리한다.
- 화이트리스트는 DB 컬럼 하나 또는 이메일 목록 수준으로 시작한다.
- 별도 어드민 UI는 만들지 않는다.

크레딧 사용 로그:

- 별도 독립 기능이 아니라 크레딧 차감 로직 구현 시 자연스럽게 포함한다.
- 크레딧 소모 이벤트마다 어떤 기능에서 소모됐는지 기록한다.
- 예: `feature_type: "ocr" | "ai_meaning" | "grammar_analysis"`.
- 목적은 추후 어떤 기능이 실제로 가치 있는지 행동 데이터로 판단하기 위함이다.
- 초기에는 관리자 화면 없이 DB 기록만 남긴다.

#### 2. 현재 UX 문제 해결

왜 이 순서인가: 첫인상과 실제 사용 지속 여부에 바로 영향을 주기 때문입니다.

범위:

- 단어 목록 버튼 정리
- 노트 관리 UI 분리
- OCR 저장 전 확인 개선
- 버튼 라벨 정리
- 단어/문장 콘텐츠가 버튼보다 먼저 보이도록 정리

#### 3. 문법/표현 카드 MVP

왜 이 순서인가: 단순 단어장과 구분되는 차별화 스토리의 핵심이기 때문입니다.

범위:

- 기존 단어 타입과 구분되는 문법/표현 카드 타입을 만든다.
- 최소 스펙은 문법 패턴, 의미, 접속 방식, 원문 예문으로 제한한다.
- 원어민 선호 표현 코멘트를 포함한다.
- 원어민 선호 표현은 “사전적으로 가능한 말”보다 “실제 일본어 원어민이 해당 상황에서 자연스럽게 쓰는 표현”을 짚어주는 필드다.
- AI가 후보를 제안하고 사람이 검수하는 운영 방식을 전제로 한다.
- 원문 기반 예문을 강조한다.
- 이때 예문은 AI가 새로 창작한 문장이 아니라 OCR로 캡처한 원문 자체를 실사용 예문으로 활용한다.
- 학습자가 자기 지식 범위 안에서만 예문을 만드는 한계를 보완하는 것이 목적이다.
- 이미 OCR 원문과 source sentence를 저장하는 흐름이 있으므로 추가 개발 스코프는 크지 않다.

예:

```text
暗め
문법 패턴: 〜め
의미: 조금 ~한 편 / ~쪽에 가까운
접속: い형용사 어간 + め
원문 예문: 写真は暗めだけど、雰囲気はいい。
원어민 선호 표현: “조금 어두운 편”처럼 완곡하게 정도를 말할 때 자연스럽다.
```

#### 4. 상황극 프롬프트 생성 기능, 전자 방식

왜 이 순서인가: API 비용 없이 저장된 단어의 활용 가치를 바로 보여줄 수 있기 때문입니다.

범위:

- 저장된 단어 또는 노트를 선택한다.
- 외부 LLM에 붙여넣을 수 있는 상황극 프롬프트를 생성한다.
- 앱은 직접 AI API를 호출하지 않는다.
- 생성된 텍스트를 클립보드로 제공한다.
- 프롬프트 조립 로직은 서버 사이드에서 처리한다.
- 템플릿 노출을 줄이고 추후 유지보수를 쉽게 한다.
- 단어가 50개 이상처럼 많으면, 앱이 직접 클러스터링하지 않는다.
- 프롬프트 안에서 ChatGPT에게 의미 단위로 그룹을 나누고 순차적으로 진행하라고 지시한다.

### 2차 범위: 1차 검증 후

1차 범위로 실제 사용자가 앱을 계속 쓸 이유가 확인되면 진행합니다.

#### 1. OCR 문장 수정/합치기/나누기

왜 이 순서인가: OCR 입력이 늘어나면 자동 문장 분리 오류가 실제 불편으로 드러날 가능성이 높기 때문입니다.

범위:

- 추출 텍스트 수정
- 문장 재분리
- 문장 합치기
- 문장 나누기
- 저장 전 문장 기준 정리

#### 2. 시트 보기 MVP

왜 이 순서인가: 아이패드/데스크탑에서 단어를 많이 훑는 사용성을 제공해 앱의 학습 밀도를 높이기 때문입니다.

범위:

- 노트별 시트 보기
- 단어/읽기/뜻/예문 컬럼
- 뜻 가리기
- 읽기 가리기
- 예문 표시/숨김
- 검색

#### 3. JLPT 레벨 태깅

왜 이 순서인가: 이미 쌓인 단어/문법 카드 데이터를 시험 준비 관점으로 재활용할 수 있기 때문입니다.

범위:

- 신규 콘텐츠 제작이 아니라 기존 단어/문법 카드에 JLPT 레벨 태그를 붙인다.
- 레벨은 `N5`, `N4`, `N3`, `N2`, `N1` 범위로 둔다.
- 사용자는 N3, N4 등 시험 준비 목적에 맞게 필터링할 수 있다.
- 시중 단어장이 실제 시험 난이도 대비 과도하게 넓은 어휘 범위를 다루는 문제를 보완한다.
- 앱은 실제 원문에서 캡처된 데이터 기반 필터를 제공하는 방향으로 차별화한다.
- AI가 레벨 후보를 제안하되, 정확도가 중요하므로 사람이 검수할 수 있는 구조를 전제로 한다.

### 3차 범위: 장기 검토, 지금 설계하지 않음

아이디어는 좋지만 지속 가능성 또는 필요성이 아직 검증되지 않은 영역입니다. 지금은 구체 구현 설계를 하지 않습니다.

#### 1. 근대문학 독해 콘텐츠

왜 이 순서인가: 콘텐츠 제작이 지속 가능한 노동 구조인지 아직 검증되지 않았기 때문입니다.

검토 방식:

- 작품 1개만 선택한다.
- 문장 20~30개 수준의 미니 프로토타입을 만든다.
- 원문 저작권 상태를 확인한다.
- 번역/해설은 직접 제작하거나 자체 생성/검수한다.
- 원문 공개 여부, 출처 표기, 번역/해설 권리를 확인한다.

#### 2. 소셜 로그인

왜 이 순서인가: 이메일 가입 마찰이 실제 유저 확보의 장애로 드러난 뒤 도입해도 늦지 않기 때문입니다.

검토 조건:

- 실제 유저가 이메일 가입을 불편해한다.
- 재방문/로그인 이탈 문제가 발생한다.
- Google/Apple 로그인 연결 필요성이 분명해진다.

#### 3. 정식 어드민 페이지

왜 이 순서인가: 초기에는 화이트리스트/DB 직접 관리로 충분하고, 어드민은 보안/운영 비용이 크기 때문입니다.

검토 조건:

- 유저 수가 늘어 수동 관리가 어려워진다.
- 환불/크레딧 조정/사용량 확인이 반복적으로 필요해진다.
- 어드민 audit log와 권한 관리가 필요한 시점이 온다.

#### 4. 청해·독해 연습문제 생성

왜 이 순서인가: 아이디어 가치는 있지만 제작 노동, 저작권, 품질 캘리브레이션 리스크가 커서 별도 검증이 필요하기 때문입니다.

주의:

- JLPT 공식 사이트가 무료로 제공하는 것은 샘플 문제 2회분 수준이다.
- 여러 해의 기출문제를 무료로 공식 제공하는 구조가 아니다.
- 실제 기출 지문이나 문제를 그대로 사용하는 것은 저작권 침해이므로 절대 사용하지 않는다.
- AI가 완전히 새로 만드는 오리지널 지문/문제로 가야 한다.
- 시험 특유의 문체와 난이도 캘리브레이션이 까다롭다.
- 청해는 TTS 음성 생성까지 필요해 사실상 별도 프로덕트 수준의 작업량이다.

검토 방식:

- 특정 레벨 1회분 정도의 미니 프로토타입으로 먼저 검증한다.
- 문제 품질, 난이도, 해설 품질, 제작 시간을 확인한다.
- 지속 가능한 제작 구조가 보일 때만 본격 기획한다.

### 보류: 문서에만 남기고 지금 손대지 않음

#### 1. JLPT/토익 등 대형 교육기업과의 B2B 라이선싱

왜 보류인가: 공식 단어 리스트 비공개, 기존 사업자와의 이해관계 충돌, 영업 난이도 때문에 현재 사이드 프로젝트 범위와 맞지 않기 때문입니다.

메모:

- 대형 교육기업 B2B는 현실성이 낮다.
- 대신 개인 크리에이터/강사와의 소규모 제휴가 더 현실적이다.
- 저작권 이슈가 없는 자체 큐레이션 콘텐츠 제작도 대안이다.

#### 2. 외국인 대상 한국어 학습 버전

왜 보류인가: 기술적으로는 다국어 탭 구조가 있어 확장 가능하지만, 타겟 유저와 마케팅 채널이 완전히 달라 별도 사업에 가깝기 때문입니다.

메모:

- 일본어 버전이 안정된 이후 검토한다.
- 현재는 일본어 학습 경험과 OCR/문법/표현 카드 완성도가 우선이다.

## 8. 검증 및 출시 전략

사전 설문조사는 진행하지 않습니다.

이유:

- 타겟 유저층은 일본어 스터디 모임, 가족, 가까운 학습자처럼 이미 어느 정도 명확하다.
- 도구형 앱은 설문 응답보다 실제 사용 관찰이 훨씬 정확한 신호를 준다.
- 사용자가 “쓸 것 같다”고 말하는 것보다, 실제로 OCR을 쓰고 단어를 저장하고 다시 돌아오는지가 중요하다.

검증 순서:

1. 1차 범위 완성 후 기존 커뮤니티 안의 3~5명에게 먼저 사용하게 한다.
2. 직접 관찰하거나 짧은 대화로 피드백을 수집한다.
3. 큰 문제 없으면 블로그, X 등 기존 채널을 통해 더 넓은 범위로 공개한다.
4. 이후부터는 크레딧 사용 로그, OCR 사용 횟수, AI 자동완성 사용 횟수, 저장/복습 행동 같은 실제 데이터를 기준으로 기능 우선순위를 조정한다.

검증에서 볼 핵심 신호:

- 사용자가 OCR을 실제로 반복해서 쓰는가?
- 저장 전 확인 과정에서 이탈하지 않는가?
- 문법/표현 카드가 단어 카드보다 더 기억에 남는 차별점이 되는가?
- 상황극 프롬프트를 실제 학습에 붙여넣어 쓰는가?
- 무료 크레딧 제한이 너무 빡빡하거나 너무 느슨하지 않은가?

## 9. 디자인 진행 방식

정식 디자인 외주는 지금 단계에서 진행하지 않습니다.

이유:

- 아직 지속 사용 여부가 검증되지 않았다.
- 첫 타겟은 이미 니즈를 아는 소규모 커뮤니티다.
- 이 단계에서는 완성도 높은 비주얼보다 기능 검증과 사용 흐름 확인이 우선이다.

1차 범위 진행 방식:

- AI 코딩 도구를 활용해 자체 제작한다.
- 기존 `6. 디자인 원칙` 내용을 프롬프트에 반영해 UI를 개선한다.
- 버튼 수를 줄이고, 텍스트/단어/문장이 주인공이 되도록 한다.
- 사용자가 실제로 어디서 막히는지 먼저 확인한다.

정식 디자인 외주를 고려할 시점:

- 소규모 베타 검증을 통과하고 더 넓은 유저층에 공개할 준비가 되었을 때.
- 자체 제작 결과물에서 구체적으로 어떤 화면이 이탈 원인인지 파악되었을 때.
- 디자이너에게 “예쁘게 해주세요”가 아니라 “이 화면의 이 문제를 해결해주세요”라고 말할 수 있을 때.

## 10. 디자이너에게 전달할 핵심 질문

- 단어 목록에서 버튼을 얼마나 숨길 것인가?
- 노트 선택과 노트 관리를 어떻게 분리할 것인가?
- 단어 카드에서 수정/상태 버튼을 어디까지 노출할 것인가?
- OCR 저장 전 확인 목록은 카드형이 좋은가, compact list가 좋은가?
- 시트 보기는 학습용 표처럼 보여야 하는가, 노트처럼 보여야 하는가?
- 문장 분석 결과는 패널, 카드, 리스트 중 어떤 형태가 좋은가?
- 근대문학 뷰어는 원문 중심이어야 하는가, 해설 중심이어야 하는가?
